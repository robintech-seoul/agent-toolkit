Claude Code 플러그인

설정을 대신 해주는 에이전트로 배포하세요.

robin-cloud-onboarding 플러그인이 당신의 repo를 읽어 배포 파일을 만들고, 콘솔을 단계별로 안내하고, 배포까지 마칩니다 — 문제가 생기면 앱 로그를 읽어 고쳐줍니다. Kubernetes도, 클러스터 접근도 필요 없습니다.

무엇을 얻나요

시크릿 없는 CI

GitHub Actions에서 repo에 시크릿 0개로 배포 — GitHub 자체 신원을 단기 빌드 자격으로 교환합니다.

매니지드 · HTTPS

매니지드 Kubernetes 위에서 컨테이너 실행, TLS 인증서 자동 발급 — 갱신할 것이 없습니다.

내 도메인

DNS 레코드 하나만 가리키면 내 도메인에서, 유효한 인증서로 서비스됩니다.

자가 치유

에이전트가 각 단계를 검증하고, 실패하면 앱 로그를 읽어 원인을 고칩니다.

어떻게 동작하나요

  1. repo 분석

    배포할 조각(프론트·관리자·API…)을 스택·빌드 명령·포트와 함께 파악합니다.

  2. 파일 생성

    조각마다 Dockerfile, 키리스 CI 워크플로, nginx 설정, .dockerignore를 만듭니다.

  3. 콘솔 안내

    정확한 클릭 순서(프로젝트·GitHub 연결·이미지 저장소·배포설정·DB·도메인)를 안내하고 각각 확인합니다.

  4. 배포 · 검증

    빌드를 지켜보고, 사이트를 curl하고, 로그를 읽어 흔한 실패를 200이 나올 때까지 고칩니다.

Claude Code내 프로젝트 repo에서 실행

1단계 — 플러그인 설치

/plugin marketplace add robintech-seoul/agent-toolkit
/plugin install robin-cloud-onboarding@robintech

2단계 — 실행

내 프로젝트 repo에서:

/robin-cloud-onboarding:onboard   # 또는 그냥: "이 repo를 Robin-Cloud에 온보딩해줘"

이후는 에이전트가 진행합니다. 당신 몫은 에이전트가 하나씩 알려주는 콘솔 클릭, 에이전트 몫은 파일 작성·빌드·검증입니다.

repo에 생성되는 것

  • <컴포넌트>/Dockerfile — 이미지마다 하나(nginx 뒤 정적 SPA, Python/Node 서버 등).
  • <컴포넌트>/nginx.conf — 프론트용(루트 또는 서브패스).
  • .github/workflows/deploy-robin-cloud.yml — 키리스 배포 파이프라인, 시크릿 0개.
  • .dockerignore.

콘솔에서 할 일

에이전트가 언제 무엇을 할지 정확히 알려줍니다 — 순서대로:

  1. 프로젝트 생성

  2. GitHub 연결

    “GitHub App으로 연결” → 내 repo에 설치 → 승인.

  3. 이미지 저장소 생성

    컴포넌트마다 하나.

  4. 배포설정 저장

    포트와 각 조각이 서비스될 경로.

  5. DB 생성 · 시크릿 설정

    서버가 있다면.

  6. 도메인 연결

    선택.

문제가 생기면

혼자 디버깅하지 않습니다. 에이전트가 설정 때 만든 그 로그 API 키로 HTTPS로 파드 로그를 당겨, 흔한 원인(잘못된 드라이버의 DB URL, 누락된 시크릿, 미실행 마이그레이션, 포트 불일치)을 알아채고 고친 뒤, 앱이 200을 낼 때까지 다시 확인합니다.

알아두면 좋은 것

URL에 포트가 없습니다. 클러스터 내부에서는 8080으로 돌지만, 접속은 일반 HTTPS — https://내도메인/, 절대 :8080 아님.

커스텀 도메인? 그 도메인의 DNS A 레코드를 3.35.86.196(Robin-Cloud 게이트웨이)으로 가리키고, 배포설정의 ingress host에 지정하면 — TLS는 자동 발급됩니다.

서브패스의 두 번째 앱(예: 관리자 /admin)은 끝에 슬래시를 붙여 접속: https://내도메인/admin/.

Robin-Cloud· onboarding

Claude Code plugin

Deploy your project with an agent that does the setup.

The robin-cloud-onboarding plugin reads your repo, writes the deploy files, walks you through the console, ships it — and if anything breaks, reads your app's logs and fixes it. No Kubernetes, no cluster access on your side.

What you get

Keyless CI

Deploys from GitHub Actions with zero secrets in your repo — GitHub's own identity is exchanged for short-lived build credentials.

Managed & HTTPS

Containers on managed Kubernetes with automatic TLS certificates — nothing to renew.

Your own domain

Point one DNS record and you're live on your domain, with a valid certificate.

Self-healing

The agent verifies each step and debugs failures straight from your pod logs.

How it works

  1. Analyzes your repo

    Finds each deployable piece — frontend, admin, API — with its stack, build command, and port.

  2. Generates the files

    A Dockerfile per piece, a keyless CI workflow, nginx config, and .dockerignore.

  3. Guides the console

    Hands you exact clicks — project, GitHub connect, image repos, deploy config, database, domain — and confirms each one.

  4. Deploys & verifies

    Watches the build, curls your site, reads the logs, and fixes common failures until it answers 200.

Claude Coderunning in your project repo

Step 1 — Install the plugin

/plugin marketplace add robintech-seoul/agent-toolkit
/plugin install robin-cloud-onboarding@robintech

Step 2 — Run it

In your project repo:

/robin-cloud-onboarding:onboard   # or just: "onboard this repo to Robin-Cloud"

The agent takes over. Your part is the console clicks it hands you, one at a time; its part is writing the files, running the build, and verifying.

What it writes in your repo

  • <component>/Dockerfile — one per image (a static SPA behind nginx, a Python/Node server…).
  • <component>/nginx.conf — for frontends, at the root or a subpath.
  • .github/workflows/deploy-robin-cloud.yml — the keyless deploy pipeline, no secrets.
  • .dockerignore.

What you'll do in the console

The agent tells you exactly when and what — in order:

  1. Create the project

  2. Connect GitHub

    “GitHub App으로 연결” → install on your repo → approve.

  3. Create image repos

    One per component.

  4. Save the deploy config

    Ports and the path each piece is served at.

  5. Create a database & set secrets

    If you have a server.

  6. Point your domain

    Optional.

If something breaks

You don't debug alone. The agent pulls your pod logs over HTTPS — the same log API key from setup — recognizes the usual culprits (a database URL on the wrong driver, a missing secret, an un-run migration, a port mismatch), fixes them, and re-checks until your app answers 200.

Good to know

URLs have no port. Everything runs on 8080 inside the cluster; you reach it over normal HTTPS — https://yourdomain/, never :8080.

Custom domain? Point its DNS A record to 3.35.86.196 (the Robin-Cloud gateway), then set it as the ingress host in the deploy config — TLS is issued automatically.

A second app at a subpath (e.g. an admin at /admin) is reached with a trailing slash: https://yourdomain/admin/.
